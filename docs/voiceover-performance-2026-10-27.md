# 配音卡顿与失败排查（2026-10-27）

## 现场证据

- 本机为 16 GB 统一内存的 Apple M1 Pro。排查期间交换空间占用约 14–25 GB，同时有其他程序进行多进程视频生成与编码；这些进程未被终止。交换空间占用反映内存压力历史，不能单独作为当前卡顿的量化指标。
- 张良项目最近两次配音任务包含约 600 秒后失败的片段，错误显示“任务已取消”。实际是任务管理器的十分钟超时触发中止，但 Python 适配器和本地队列把超时原因覆盖成了取消。
- 原 MLX 配置没有限制可回收缓存；默认内存指导值在这台机器上接近整机内存，模型推理容易与桌面及其他任务争用内存。模型加载实测约 6–11 秒，不能解释每镜 200–600 秒的等待。
- VoxCPM2 原来对短句也允许生成 1500 个 token（约 120 秒音频）。模型没有正常收尾时，短句也可能一直推理到超时。
- 实际 Electron 测试向当前分镜页面连续发送三次任务进度更新，iframe 移除与新增次数均为零，排除了这条重复加载假设。本次没有基于该假设修改渲染器或禁用 GPU。

## 修改

1. 模型加载前将 MLX 内存指导值设为推荐值与物理内存一半的较小值，并将可回收缓存限制为 128 MiB。内存指导值不是操作系统硬上限；模型和推理的实际内存仍受文案长度及引擎影响。
2. VoxCPM2 根据文案长度设置保守的生成上限：至少 12 秒，随字符数增长，最多 120 秒。正常结束的生成不受影响；达到上限仍未正常结束的结果明确报错，不把截断音频存为成功。
3. 贯穿 Worker、本地队列与任务管理器保留超时原因，界面区分“生成超时”和用户取消。工作流错误同时标记失败分镜与段落。
4. 整段配音失败后，同输入版本重试会逐段查找已成功的配音任务。只有文案、分镜、引擎、音色版本、造声描述、全部归一化参数及文件哈希均一致才复用；修改文案、音色或文件后重新生成。单段主动重新生成仍会生成新的结果。
5. 在生成记录与素材元数据增加模型加载耗时、MLX 峰值内存，方便后续定位问题。

没有修改用户音色、参考音频、参考转写、采样步数、CFG 或随机种子，没有自动审核或发布视频。

## 验证

- 使用最近失败的第三镜原文案、原参考音频、原参数进行真实 VoxCPM2 对照，结果写入独立探针目录，没有向生产数据库插入配音任务。
- 原配置一次耗时 84.414 秒，限制缓存后一次耗时 60.399 秒；两份音频均为 11.520167 秒，逐采样比较完全一致。优化后记录的 MLX 峰值约 6.5 GiB。不同时间的系统负载有差异，这一组观测不能保证每次提速相同比例。
- `pnpm test:voiceover`：39 项通过，包含超时原因保留。
- `pnpm test:video-workflow`：74 项通过，包含失败重试复用及文案、音色、文件变化后重新生成。
- `pnpm test:voice-runtime`：7 项通过，包含内存配置与文案生成预算。
- `pnpm build`、受影响 TypeScript 服务文件 ESLint、`git diff --check` 通过。
- 全量 `tsc -b` 仍有 82 条既有诊断，本次修改的配音和工作流音频服务文件没有诊断；没有修复无关模块。

该机器上的本地模型仍非实时合成。其他程序大量使用统一内存或编码时，仍会影响交互与生成速度；缓存限制不会释放其他程序占用的内存。
